## 1. System Purpose

A B2B SaaS platform sold to educational consultancies (Admins). Each consultancy (tenant) manages their own students and counselors. Students receive AI-driven admission predictions and professional reports. Counselors provide guided session management. Super Admin oversees the entire platform and monetizes via sponsored college placements.

## 3. Multi-Tenant Model

**Tenant = Admin**

- Each Admin registers as an independent tenant
- All data created under an Admin is scoped to `tenant_id = admin.id`
- Counselors are sub-users of an Admin tenant
- Students are sub-users managed within a tenant
- No cross-tenant data leakage is permissible at any layer

**Enforcement Layers:**
1. Database — Row-Level Security (RLS) in Supabase
2. API — Middleware injects `tenant_id` from JWT; all queries filter by it
3. UI — Role-based rendering; no cross-tenant navigation

## 4. Role Hierarchy

```
SuperAdmin (1 platform owner)
    └── Admin (N tenants, each independently isolated)
            └── Counselor (N counselors per Admin)
                    └── Student (N students per Counselor/Admin)
```

**Access Matrix:**

| Resource          | SuperAdmin | Admin       | Counselor     | Student      |
|-------------------|-----------|-------------|---------------|--------------|
| All Admins        | Full      | None        | None          | None         |
| Own tenant data   | Read      | Full        | Assigned only | Own only     |
| Students          | Read all  | Own tenant  | Assigned only | Own profile  |
| Counselors        | Read all  | Own tenant  | Own profile   | None         |
| Cutoff data       | Read      | Full (own)  | Read          | Read         |
| Predictions       | Read all  | Own tenant  | Assigned      | Own only     |
| Reports           | Read all  | Own tenant  | Assigned      | Own only     |
| Sponsored colleges| Full      | Configure   | None          | View tagged  |
| Notifications     | Create all| Own tenant  | Own students  | Receive      |

## 5. AI Prediction Engine Logic

**Inputs:**
- Student score / percentile / rank
- Category (General / OBC / SC / ST / EWS)
- Preferred branch
- College selection
- Round number (1–6)
- Historical cutoff data (uploaded by Admin)

**Computed Metrics:**
- Average cutoff over N years
- Trend shift (year-over-year delta)
- Demand variation (seat fill ratio)
- Score difference (student score vs. cutoff average)

**Classification:**
| Score Diff | Risk Level | Probability Range |
|------------|-----------|-------------------|
| > +5%      | Low       | 75–95%            |
| ±5%        | Medium    | 40–70%            |
| < -5%      | High      | < 30%             |

**Outputs:**
- Probability percentage
- Confidence score (0–1)
- Classification: Dream / Safe / Backup
- Risk level: Low / Medium / High
- Strategy suggestion (text)

## 6. Report Architecture

### Report Type 1: Student Probability Report (`student_summary`)
- Generated by: Student (self-serve)
- Audience: Student
- Content: Abstract summary, probability, risk meter, recommended colleges, sponsored college tags, strategy suggestion
- Style: Clean, minimal, student-friendly
- Stored: `reports` table with `report_type = 'student_summary'`

### Report Type 2: Counselor Detailed Report (`counselor_detailed`)
- Generated by: Counselor
- Audience: Counselor + Admin
- Content: Full profile, exam analysis, historical cutoff comparison, trend insights, round-wise table, strategy roadmap, counselor remarks, meeting notes
- Style: Professional, data-heavy, PDF-exportable
- Stored: `reports` table with `report_type = 'counselor_detailed'`
- Versioned: `version` column increments on each regeneration

**Both reports are scoped to `tenant_id` — no cross-tenant report access.**

## 7. Sponsored College Logic

- Super Admin adds platform-wide sponsored colleges
- Admin can activate/configure per-tenant sponsored colleges with custom `bias_weight`
- Sponsored colleges get priority boost in prediction recommendations
- Clearly labeled as "Sponsored" in UI and reports
- Revenue tracked via `sponsored_performance` table (impressions, clicks, report inclusions)

## 8. Security Architecture

| Security Layer | Implementation |
|----------------|----------------|
| Authentication | Email + Password (bcryptjs, salt 12) + JWT |
| Authorization  | Role-based middleware on every route |
| Data isolation | `tenant_id` injected from JWT on every DB query |
| RLS            | Supabase RLS (backup layer, Phase 10 hardening) |
| API protection | validateJWT middleware on all protected routes |
| Document access| Supabase signed storage URLs (time-limited) |
| Password policy| Minimum 8 characters, bcrypt hashed |

> OTP authentication removed from scope by design decision. Simple email+password auth used instead.

---

## 9. Key Architectural Decisions

| Decision | Choice | Reason |
|----------|--------|--------|
| Database | Supabase (PostgreSQL) | RLS support, real-time, hosted |
| Auth strategy | OTP + JWT | No password storage risk, stateless API |
| Tenant model | Shared DB, tenant_id column isolation | Cost-effective at scale, RLS enforced |
| AI engine | Custom Node.js service | Full control over algorithm |
| PDF generation | Puppeteer (server-side) | Consistent rendering across devices |
| Frontend hosting | Vercel | Edge CDN, CI/CD integration |
